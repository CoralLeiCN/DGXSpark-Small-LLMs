## Observations and diagnosis

The following nonfatal startup warnings recurred:

```text
Failed to get GPU memory capacity from nvidia-smi. Falling back to torch.cuda.mem_get_info().
Reported total GPU memory per device (MiB): [124610]
torchcodec is not installed; audio inputs will fail at request time
Using FP8 KV cache but no scaling factors provided. Defaulting to scaling factors of 1.0.
```

The runtime used its PyTorch memory fallback and proceeded to weight loading.
The missing optional audio dependency is not exercised by this text experiment.
No audio request or dependency change was attempted. The legacy
`python -m sglang.launch_server` entrypoint also emitted its deprecation advisory.
The draft KV scaling warning is a quality limitation; small smoke checks do not
establish full quality equivalence.

Startup completed at 20:21:53 UTC, but reported:

```text
max_running_requests is capped to 69 by the mamba state cache
(max_mamba_cache_size=276, 4 state slots per request).
```

The target loaded in 111.83 seconds (20.63 GB reported weight allocation),
and the native `Qwen3_5ForCausalLMMTP` loaded in 4.85 seconds (5.62 GB before
subsequent embedding/head sharing). The Mamba allocation was 0.76 GB convolution,
38.95 GB SSM, 29.53 GB intermediate SSM, and 0.32 GB intermediate convolution.
Target and draft KV capacity was 230,274 tokens. All four graph captures
completed, leaving 8.72 GB reported available GPU memory. Docker reported
healthy, zero restarts, and no OOM.

Reading `/opt/dgxspark/start.sh` inside the container confirmed why the intended
288 slots were absent. The next startup must pass `--max-mamba-cache-size 288`
explicitly, along with the intended ratio `--mamba-full-memory-ratio 4.59`.

The first shell-background `nohup docker logs --follow` process did not survive
the command session. A durable user service,
`qwen-nvfp4-mtp2-20260925-logs.service`, replaced it, replaying Docker's retained
startup log and continuing to append to `server.log`. No retained container log
was lost. The benchmark will likewise run under a user service rather than a
shell-background process.

The Responses API returned `completed` and `DGX Spark NVFP4 ready`.

The initial smoke script then failed its metric assertion:

```text
assert steps and all(float(value) == 2 for value in steps), steps
AssertionError: ['0.0']
```

This was a validation timing issue: short replies had made only 13 speculative
verification calls, while configuration/acceptance gauges refresh during the
periodic decode report. The metric reporter source and subsequent longer request
confirmed that interpretation. The revised script, saved separately under
`qualification-confirmation/`, repeated the four checks and forced a 128-token
reply. All five checks passed (exit 0), and the saved metrics showed:

- `sglang:spec_num_steps=2`, `sglang:spec_num_draft_tokens=3`;
- `sglang:spec_verify_calls_total=75`;
- last reported `sglang:spec_accept_length=2.4`, `sglang:spec_accept_rate=0.7`.

Those acceptance values describe this smoke workload only, not a benchmark.
The service was stopped normally before any AIPerf sweep; its Docker state and
complete shutdown log were saved. Shutdown emitted the familiar process-group
cleanup warning and ASGI `SystemExit: 0` / `CancelledError` traceback; Docker
reported exit code 0 and `OOMKilled=false`.

## Lesson

Preserve experiment processes independently of the interactive command session.
For NVFP4 native MTP, validate actual loading, admission, and speculative metrics
before interpreting a successful container creation as a working experiment.
Check the embedded image launcher against the checkout. For speculative metrics,
also cross a decode-report interval instead of treating initialized zero gauges
as proof that MTP is disabled.
